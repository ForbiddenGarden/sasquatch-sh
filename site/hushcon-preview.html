ELINKER — THE GHOST PROCESS

/home/elinker/bin/elinker — a 364 KB ARM ELF binary not named or referenced in any public documentation. It owns the entire RF ↔ cloud path.

  • > Receives RF heartbeats from all 4 radios
  • > Multiplexes uplink to eslworking over TLS
  • > Routes server downlinks to specific radios
  • > Own OpenSSL 1.0.2d TLS client (2015-era)
  • > SSL is opt-in and off by default
SILENT FIRMWARE REVERT

If any radio fails its version-query during elinker’s startup, it silently reflashes that radio back to stock — no human action, barely-visible log lines, no alarm. A boot hiccup can undo a firmware change with no indication anything happened.

MORE ALARMING FINDINGS
  • > firmwareupgrade.sh: RSA-SHA1 sig check, but $filename used unquoted — shell injection
  • > elinker.sh restart has a PID-file race — can leave zero elinker running
  • > Our unit was last configured for aldi-sued-prd.hanshowcloud.net

The Protocol
Off-the-Shelf “Proprietary”

Hanshow’s RF protocol isn’t proprietary engineering — it’s a turnkey ESL reference design from Telink, configured and shipped. The chip, the radio, and the protocol are all commercially available.

THE MCU: TELINK TLSR8359
Arch
TC32 — Telink’s own 32-bit core, not ARM Cortex
Why
avoids ARM licensing fees entirely
Radio
integrated 2.4 GHz multi-mode transceiver
SDK
tc_platform_sdk — full RF demo code included

Telink markets a complete ESL reference design around this chip — tag firmware, AP firmware, protocol stack, even the EPD drivers. Hanshow’s product is built on that reference.

THE RF: SHOCKBURST REIMPLEMENTATION
Protocol
RF_PRIVATE_500K — Telink’s “proprietary mode”
Based on
Nordic Enhanced ShockBurst architecture
PHY
500 kbps GFSK, 5× bit-expansion → 100k logical
Sync
2–5 byte access code, hardware correlator
Pipes
6 RX pipes — Nordic uses 8
Framing
reg 0x404 |= 0x03 — “private header mode”

Nordic ESB: configurable access address (2–5 bytes), multi-pipe RX filtering, 250k/1M/2M data rates, hardware CRC. Telink’s RF_PRIVATE mode: same access-code/pipe abstraction, same address lengths, same rates + 500k, same register-level pattern. The SDK even calls it “ShockBurst Mode 3.” Not bit-compatible — a clean-room architectural clone.

Not ARM — TC32 core avoids licensing Not Nordic — ShockBurst architecture reimplemented Telink ESL ref design = complete turnkey product

THE CRITICAL INSIGHT

An unprovisioned tag ignores ctrl=0x93 entirely. Phase 1 sets a readiness flag at SRAM 0x8432d0 that gates the commission handler. Without it, the tag never replies.

ATTACK SURFACE

NFC: no authentication — CRC-16 only, no MAC/HMAC. RF: AES-128-ECB optional, default key 0xFF × 16. Firmware: no signature verification.

Phase 0
NFC Handshake

Private protocol over ISO 14443-4A. Two-step handshake opens the session gate.

FRAME FORMAT
[00] [C0] [00] [len] [reqtype]
[content(0..240)]
[crc16_lo] [crc16_hi]
CRC-16/XMODEM (poly 0x1021, init 0x0000)
HANDSHAKE
  1. 1. getRandom (0x02) — send challenge, get 16-byte nonce
  2. 2. getSendRandom (0x08) — encrypt nonce back, get 9000
All 8 tags share the same default key: 0xFF × 16 — and a static nonce that survives power cycles
Phase 1 — The Breakthrough
Finding the Gate

We spent weeks trying to commission tags that silently ignored every RF request. The firmware told us why.

THE DEAD END
  • > Tags receive ctrl=0x93 commission frames…
  • > The dispatch table has an entry for it…
  • > But the handler checks a flag first
  • > Flag at 0x8432d0 is zero from BSS init
THE KEY
  • > Only one code path in 512 KB writes to 0x8432d0
  • > TLV sub-record 0x35 via NFC opcode 0x11
  • > Normally sent by the server during initial setup
  • > We can send it ourselves via Flipper Zero NFC

Our responder must reply within 51 ms of each tag burst.
